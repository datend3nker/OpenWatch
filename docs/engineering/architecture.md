# Architecture

## Purpose

OpenWatch is a phone app that owns the devices, a watch app, and the link between the two.
This document is the map of the phone app and the rules that hold across it. The device layer
came from OpenVitals unchanged where it could; the sections below are its sections, with the
OpenWatch seams noted.

## Current Snapshot

- App namespace: `tech.mmarca.openwatch`
- Build logic: `build-logic/`, an included build with the convention plugins every module applies (`openwatch.android.application`, `openwatch.android.library`, `openwatch.jvm.library`, and `openwatch.robolectric` for a library whose tests run on Robolectric): SDK levels, Java 17, signing from the environment, the debug, release and nightly build types, lint and dependency locking. A module's own file holds only what is its own (version codes, the `ci` type, the diagnostics flag). A change there must leave the release APKs byte-identical; compare their hashes before and after.
- Project shape: twenty-eight Gradle modules. The phone app is `:app`, the shell ([Phone modules](#phone-modules)):
  the application, the activities, the navigation and the Hilt root. The screens are the
  `:feature:*` modules; `:core:model` and `:core:fit`
  hold the pure code the app depends on (below); `:core:devices-api` the device contracts
  ([`devices/core`](#devicescore)); `:core:health-api` how the devices talk to Health Connect
  ([rule 3](#3-health-connect-is-reached-through-healthconnectgateway-only)); `:core:health`
  Health Connect as the app reaches it, which implements those contracts (the gateway, the record
  sink, the activity writes, the sync gate, the data catalog; [rule 3](#3-health-connect-is-reached-through-healthconnectgateway-only)); `:core:ui`
  what every screen shares (the theme, the shared components, `core/presentation`'s formatters
  and `ScreenError`, `core/permissions`); `:core:data` what the phone keeps (the Room database, the registry,
  the per-device state, the preferences; [below](#module-coredata)); `:devices:core` the
  platform half every device family shares ([below](#module-devicescore)); `:devices:garmin`,
  `:devices:wearos`, `:devices:xiaomi` and `:devices:ble-standard` are the families' platform halves, device modules that bind
  themselves ([`devices/garmin`](#devicesgarmin), [`devices/wearos`](#deviceswearos), [`devices/xiaomi`](#devicesxiaomi), [`devices/blestandard`](#devicesblestandard)); `:devices:garmin:protocol`,
  `:devices:xiaomi:protocol` and `:devices:ble-standard:protocol` are the Garmin protocol, the S400 codec and the standard profiles' bytes, pure Kotlin
  ([`devices/garmin`](#devicesgarmin), [`devices/xiaomi`](#devicesxiaomi), [`devices/blestandard`](#devicesblestandard)); `:link-host` is the OpenLink host ([below](#openlink-host-link-composite-build-openlink)); `:wear` is the Wear OS watch app
  with its own CI gate; `:wearlink` is the pure-Kotlin link both apps depend on. Package names
  are the same across `:app` and the modules under `core/`, `devices/` and `feature/`. The health calculations, shared with OpenVitals,
  come from the `health-calculations/` submodule, a composite build (below).
- The watch app's pure core is `:wear:recording-core`, plain Kotlin in `wear/recording-core/`
  with the watch app's package names; only `:wear` depends on it (below).
- Dependency wiring: Hilt in `:app`, rooted at `OpenWatchApp`; modules are `di/AppModule.kt`,
  `di/RepositoryModule.kt`, `di/DevicesModule.kt` and `di/LinkModule.kt`, each device
  module's own (`GarminModule`, `WearOsModule`, `XiaomiScaleModule`, `BleStandardModule`), and the
  screen modules' (a family's screens bind their contributions, `GarminFeatureModule`,
  `WearOsFeatureModule`, `XiaomiScaleFeatureModule`; `:feature:device` declares the maps), which
  the graph installs from the modules' classes ([Hilt wiring](#hilt-wiring)).
- UI stack: Jetpack Compose + Material 3 + Navigation Compose + `ViewModel` + coroutines.
- Health data backend: the Health Connect AndroidX client, behind
  [`HealthConnectGateway`](../../core/health/src/main/kotlin/tech/mmarca/openwatch/healthconnect/HealthConnectGateway.kt).
- Room is at version 2, with five tables: `devices` (the registry) and `device_state` (what an
  integration keeps per device, gone with its device), and `garmin_wellness_samples`,
  `garmin_sleep_minutes`, `scale_weigh_ins`, each keyed by the device's id salt as well
  (`OpenWatchMigrations.MIGRATION_1_2`; a family's first device has the empty salt, so the rows
  from before belong to it).

## Device Layer

`devices/` is a layer, not a feature. It owns everything that talks to a physical device over Bluetooth and exposes ports that features consume. It has no Compose code and no navigation. The user-facing screens are the screen modules: the generic ones in `:feature:device`, a family's own in `:feature:watches-garmin`, `:feature:watches-wearos` and `:feature:scales-xiaomi` ([Phone modules](#phone-modules)).

### `devices/core`

Vendor-neutral ports plus the two things every integration shares.

The contracts are their own module, `:core:devices-api` (`core/devices-api`, pure Kotlin, same packages, linted as in the app): `DeviceClassification`, `DeviceScanClassifier`, `DeviceFamily` (with `DeviceFamilies`, `DeviceFeature` and the live readings), `RecordIds`, `ble/BleUuids`, `pairing/WatchPairingPort`, `pairing/CompanionPresenceObserver`, and in `sync/` the port and its types (`DeviceSyncPort`, `SyncFailure`), `CompositeDeviceSyncPort`, `AutoSyncInterval` and the `SyncWakeLock` seam; and the registry as a device sees it, `data/repository/contract/DeviceRegistry` (the devices and their flow, add, update, remove, the battery reading and the sync stamp), which the app's `BleDeviceRepository` implements and `di/RepositoryModule` binds. What holds Android is the module `:devices:core` ([below](#module-devicescore)): the radio lease (`RadioLease`, `RadioLeaseUse`), `DeviceLog`, `ble/BlePermissions`, the GATT link and the BLE scanner, the pairing and companion implementations, and in `sync/` `DeviceSyncController`, `SyncBudget`, `AndroidSyncWakeLock`, the schedule and its worker, and `EstimatedSleepRecord`. In `measure/`, the push path's contracts: `PushedMeasurement` (a key that names the measurement for good, and the family's own payload), `MeasurementSink` and `MeasurementOutcome`. `DevicePairing` is how a family with no add flow of its own is paired by the app's ([below](#two-ways-in-pairing-and-pushed-measurements)). Families and kinds are open sets (`DeviceIntegration` and `BleDeviceKind` in `:core:model`, persisted names with the built-in ones as constants): a family names itself and its kinds in its own module. `DeviceFamilies` keeps its `@Inject` constructor (javax.inject); Dagger in `:app` generates its factory. The module's test fixtures are the fakes the tests share: `sync/FakeDeviceSyncPort`, `pairing/FakeWatchPairing`, `FakeDeviceFamily` and `data/repository/contract/FakeDeviceRegistry` (the registry's rules in memory: one row per address, a family's first device the empty salt).

- [`RadioLease.kt`](../../devices/core/src/main/kotlin/tech/mmarca/openwatch/devices/core/RadioLease.kt) — `RadioLeaseRegistry`, one injected singleton for the process, a lease keyed **per Bluetooth address**. Two holders on different peripherals is allowed by design; two holders on the same peripheral is not.
- [`RadioLeaseUse.kt`](../../devices/core/src/main/kotlin/tech/mmarca/openwatch/devices/core/RadioLeaseUse.kt) — `registry.withRadioLease(address, owner) { ... }`, `RadioLeaseBusyException`, and `object RadioLeaseOwner` with the six owner tags: `SYNC`, `FIND`, `SETTINGS`, `NOTIFICATIONS`, `PROBE`, and `LIVE` for a live stream held while someone collects it. They are strings rather than an enum because they appear in logcat.
- [`ble/GattLink.kt`](../../devices/core/src/main/kotlin/tech/mmarca/openwatch/devices/core/ble/GattLink.kt) — one GATT connection as coroutines, the only `connectGatt` a device family makes: `peripheral()`, `dial` (up to three attempts, redialling after a stack error such as status 133 with a two-second settle pause, never after silence; 20 s each), `requestMtu`, `discoverServices`, `subscribe` (the CCCD, for notifications or, as the standard health profiles send their measurements, indications), `read` and `write` (one at a time, a write with the characteristic's own write type), `onDisconnected` and `close`. It takes no lease and decides nothing about the peripheral: its owner holds the lease for the link's whole life and decides the bond, the MTU and the characteristics between the steps. Every failure is raised as the owner's exception type (`failure`), so the Garmin stack still sees only `GarminGattClientException`. The timeouts default to the Garmin link's.
- [`ble/BleScanner.kt`](../../devices/core/src/main/kotlin/tech/mmarca/openwatch/devices/core/ble/BleScanner.kt) — the phone's one BLE scanner, both ways the device layer listens: a foreground discovery scan with a callback (`sensors/ble/BleSensorCoordinator`, the add-a-device list) and a background scan the system runs for a `PendingIntent` on service-data filters (`ServiceDataFilter`) matched in the chip (the scale). A scan opens no link and takes no lease.
- `DeviceClassification.kt` / `DeviceScanClassifier.kt` — `DeviceClassifier` and `DeviceScanClassifier` function interfaces; the first non-null classification wins, otherwise the device is a plain sensor.
- `core/pairing/` — `WatchPairingPort` (bond, unbond, associate, disassociate), its `BleWatchPairing` implementation, `CompanionDevicePairing` around `CompanionDeviceManager`, `OpenWatchCompanionDeviceService`, and `CompanionPresenceObserver`. The service is declared in `:devices:core`'s manifest, merged into the app's, and is the app's only companion service, so it is the primary one, the only one Android tells that an associated device appeared; it passes that to every observer bound `@IntoSet` in `di/DevicesModule.kt`. A second companion service, declared anywhere, would have to come after it.
- `core/DeviceFamily.kt` — one `DeviceFamily` per integration (`GarminFamily`, `WearOsFamily`, `XiaomiScaleFamily`), bound by its persisted name into the map `DeviceFamilies` reads: which registered devices are its own, what they can do (`DeviceFeature`: sync, find, live heart rate), and how one is let go. Removing a device takes its registry row and schedule, then `forget` takes its state, keys and the system's bond or association; the last Garmin device's family offers to delete its history.
- `core/sync/DeviceSyncPort.kt` — `canSync(device)` plus a progress-reporting `sync(device, trigger)`, so the watch UI never names a vendor. The trigger says who asked: `REQUESTED` (a screen, OpenLink) or `BACKGROUND` (the schedule, a file a Garmin watch announced); a Garmin watch holds a requested link 20 s for its own errands, and a background failure ends without a banner. A success counts what it wrote by kind (`SyncTally`) and lists what it left out as `SkippedSeries` (series, reason, the grants that would unblock it); a failure is a `SyncFailure` type, never a sentence, with what it wrote first as `partial`. The screens word both, in `features/watches/SyncOutcomeSummary.kt` and `SyncFailureText.kt`, the same way for every device. The worker retries only a `transient` failure. `core/sync/DeviceSyncController` runs a sync through the port, one per device at a time and devices side by side (each radio held by its own lease), for the screens, the schedule and OpenLink alike; `WatchAutoSyncScheduler` and `WatchAutoSyncWorker` are the per-device periodic sync (unique work `device-auto-sync-<id>`; the name before the move, `watch-auto-sync-<id>`, is cancelled at start). The interval comes through `AutoSyncIntervalStore`. A scheduled sync runs in its worker's coroutine under an eight-minute `SyncBudget`: an integration that reaches it at a safe point (Wear OS, between series) returns `moreRemains`, and the worker queues up to three one-time continuations (`device-auto-sync-more-<id>`). A Garmin pull has no such point inside its session; the job's stop cancels it, and the files it saved import as pending on the next run. A sync no job holds awake runs under `SyncWakeLock` (30-minute timeout). Each integration binds its own port `@IntoSet`; `CompositeDeviceSyncPort` is the one the sync controller sees and hands a device to the port that claims it.
- `core/sync/EstimatedSleepRecord.kt` — `sleepNightWindow` (18:00 the evening before to 14:00) and `estimatedSleepSessionRecord`, the Health Connect shape of a night health-calculations' `insights/SleepStageEstimator` produced from per-minute movement and heart rate. Garmin and Wear OS both write their estimates through it, each under its own id prefix and wording.

The protocol module, `:devices:garmin:protocol` (`devices/garmin/protocol`), is plain Kotlin with `explicitApi()`, in the same packages, and Android lint checks it as it did in the app (`com.android.lint`; the one baseline entry it took along is `GarminAgpsFile`'s). It holds every file of the table that touches neither Android nor the rest of the app: the byte primitives, `GarminLog` (without its logcat sink), framing, the messages and capabilities, the transports above the GATT client (`GarminTransport`, `GarminV1Transport`, `GarminMlTransport`, `GarminMlServiceChannel`, `GarminMlrChannel`, `GarminUuids`), the session, its responders, stage timers and held-sync owner, the protobuf transport and services (HTTP proxy, weather, OAuth, calendar, core location, A-GPS), file sync (`GarminDirectory`, `GarminFileSyncProtocol`, `GarminFileSyncTransfer`, `GarminFileTypes`, `GarminFileDates`, `GarminFileStore`), the uploads (`GarminFileUploader`, alarms, locations), the settings model and service, the notification messages and actions and GNCS, music messages, the realtime and navigation notices, the device names, and the FIT wellness decoders `wellness/GarminFitWellness` and `wellness/FitWellnessExtras`. The module `:devices:garmin` keeps what holds a radio, a `Context` or Health Connect: `GarminGattClient`, `GarminGattProbe`, the radio link, the notification link, forwarder and bridge, the settings link, the music and navigation relays, the stores on SharedPreferences (`GarminDeviceStateStore`, `GarminCounterWatermarkStore`, `GarminAgpsStore`) and the injected in-memory `GarminRealtimeStore`, the platform sources (`GarminCalendarSource`, `GarminPhoneLocationSource`, `GarminFindPhoneRinger`), the importers and the Health Connect mapping (`GarminActivityImporter`, `GarminDownloadImport`, `GarminLocalData`, `wellness/FitWellnessImport`, `FitWellnessExtrasImport`, `FitWellnessImporter`, `GarminSleepEstimation`), the family, the onboarding, the watch options and `GarminDeviceClassifier`.

`:devices:garmin` (`devices/garmin`, an Android library, namespace `tech.mmarca.openwatch.devices.garmin`) depends on `:devices:core` and its protocol (`api`), `:core:fit` and Hilt, and on no other family. It binds itself (`GarminModule`): its family as `GARMIN`, `GarminWatchSyncService` into the sync port set, `GarminGattRadio` to `GarminRadio`, `GarminNotificationBridge` as a presence observer and as the notification listener's one `NotificationSink`, the GATT probe, `GarminDeviceStateStore`, the one `GarminFileStore`, `GarminCounterWatermarkStore`, and its four startup actors (`garmin notifications`, `navigation`, `music`, `pruning`). The app's `DevicesModule` keeps two rules across families: its classifiers' rank before Wear OS's, and every watch's auto-sync interval kept in `GarminDeviceStateStore` under its old key. Its manifest declares `GarminFindPhoneStopReceiver`; the find-phone notification's strings are its own, with their translations. It owns its tables' contracts (`data/repository/contract/GarminWellnessRepository`, `GarminSleepMinuteRepository`, implemented by the app's Room repositories) and the one preference it reads, `GarminActivityPreferences` (the exercise type an imported activity falls back to, which `OpenWatchPreferences` implements); it takes the registry, the per-device state, the body profile and `ActivityRepository` (`:core:devices-api`) as contracts. The activity files go through `:devices:core`'s `activityimport`, whose parser, request type and conversion became public for it. Its public API is what the watch screens, OpenLink and the graph use: the family, the sync port, the radio and links (`GarminSettingsLink`, the notification bridge and its live hold), the stores and the watch options, the A-GPS import and the uploads, the onboarding use case and its outcome, the classifiers, and the protocol's types they hand over (settings, alarms, waypoints, capabilities); the GATT client stays public because the screens catch its exception. Its tests (236, over the shared fakes and the protocol's FIT test bytes) run on the JVM in the phone gate (`:devices:garmin:testCiUnitTest`).

Three edges were cut for the move to the protocol module, none of them a behaviour: `GarminLog.installLogcatSink` is an extension in the app (`GarminLogcatSink.kt`); `GarminPhoneLocationSource` left `GarminCoreLocation.kt` for a file of its own; `garminFileStore(context)`, which puts the store under the app's files dir, is the app's (`GarminFileStoreDirectory.kt`). The values the protocol takes from the platform sources, `WeatherSnapshot` (its JSON form stays in the app, `WeatherSnapshotJson.kt`) and `NotificationMsg`, and `runSuspendCatching` are `:core:model`'s. The weather and OAuth answers of the HTTP proxy are org.json: the module compiles against the reference build (`compileOnly`) and runs on the copy Android ships, so it uses only the calls that copy has. The module's test fixtures hold `wellness/FitTestBytes`, which the app's wellness import tests share.

Notes worth carrying:

- `GarminWatchSyncService` is a `@Singleton` class, not an Android `Service`, despite the name. It implements `DeviceSyncPort`.
- The GATT client prefers V2 multi-link and falls back to the direct V1 pair. V2 startup waits for `CLOSE_ALL_RESP` before registering GFDI; do not collapse the two writes into one batch.
- A logical GFDI frame is one transport write, however many BLE chunks it takes. Both transports hold their send mutex across the whole COBS frame, or concurrent traffic interleaves into corrupt frames.
- Complete protobuf messages get the extended request-id ACK; a watch that NAKs it with `LENGTH_ERROR` gets the generic ACK for the rest of the connection. Chunks always get the extended ACK. The history behind that is on `GarminProtobufTransport.extendedAcks`.
- A protobuf message over 375 bytes goes in chunks both ways. Going out, the next chunk waits for the watch to accept the last at its offset. A vívoactive 5 NAKs a reply sent whole (for message 65535, the frame being unreadable to it) and asks again a minute later: the fake OAuth tokens, 547 bytes, never arrived until outgoing messages were chunked (verified on a vívoactive 5 on 2026-11-22).
- A file pull sends `FILTER`, waits for its answer (a NAK or silence lists anyway), then requests the legacy directory. `FILTER` is sent again in reply to an announcement. An empty legacy listing on a V2 watch not yet proven legacy probes the protobuf `FileSyncService`, which streams files over a temporary reliable-ML channel. The proven protocol is remembered per device; a timeout leaves it `UNKNOWN`, never "unsupported".
- Once a session finishes or aborts its result is sealed: a kept-open link still answers the watch but ignores directory, download and announcement messages, so nothing is archived outside the result.
- Newer firmware announces recordings over `FileSyncService`, not the legacy `SYNCHRONIZATION` message. Both run the same held-link handoff; a watch whose legacy directory lists nothing is handed to the owner for a full sync instead.
- A held companion link never ends its session over a transfer. A stall cancels only the transfer (`GarminSession.cancelTransfer`), imports what was persisted, and keeps listening. The forwarder holds the radio for a transfer for at most `maxSyncHold` before yielding to a user-started sync.
- Stage timeouts are named on `GarminSession`'s constructor with their reasons; the radio's thirty-minute limit is only a whole-sync safety net, wide enough for a first sync of a watch holding months of activities. A partial pull is imported but reported as interrupted, so a dropped link is not mistaken for an empty sync.
- Link policy: the dial and the writes are `GattLink`'s, with its defaults: writes with the characteristic's own write type (with a response when the watch offers one), up to three connection attempts, redialling after a stack error such as status 133 with a settle pause between dials but never after silence. `GarminGattClient` checks the bond first, and asks for a 515-byte MTU unless the watch's `GarminDeviceStateStore.highMtu` is off, the per-address switch under "Large Bluetooth packets" on the watch screen for a watch that misbehaves with big packets.
- A watch that never sends CONFIGURATION still completes the handshake: `GarminFitCapabilities` reads `connectivity_supported` from the FIT `capabilities` record some watches push as FIT_DEFINITION and FIT_DATA messages, and `GarminSession.completeInitialisation` runs the same start-up sequence from it. Those two messages are answered with the companion's status, ACK plus the APPLIED code.
- Monitoring FIT records often carry only `timestamp_16`; resolve it to the nearest rollover in either direction (`resolveMonitoringTimestamp16`), or samples shift by 65,536 seconds.
- Logs identify protobuf traffic by type, request id, status and byte count. Never log raw protobuf, settings or unknown-message payloads: they can carry notification text, locations or credentials.
- Archiving is irreversible, and the import runs only after the whole pull, so nothing downloaded may be dropped on the way. A session that fails after a download still returns the files it has, as an abort does. `GarminFileStore.save` leaves a `.pending` note beside each file; `markImported` removes it once an import is done with the file, and the next sync imports what `pending()` still holds before it lists the watch. That covers a crash or an exception between the download and the import.
- A downloaded file's key is recorded only once the file is dealt with. The watch archives a file as it downloads, so the key is the only thing that brings it back. A workout that did not reach Health Connect (no write access, or a failed write) keeps no key, the sync reports it as a failure, and the next sync fetches it again. A file that does not convert is done with.
- A watch sync writes Health Connect records through `ImportedRecordRepository.insertImportedRecords`, the same deterministic-`clientRecordId` path the Apple Health importer uses, so a re-import upserts instead of duplicating. `data/repository/ImportedRecordWrites.kt` holds what every device writes with. The platform's Health Connect (Android 14 and newer) refuses no stored id: an equal version replaces, a lower one is kept out (`ClientRecordVersionTest`). Where a batch is refused anyway (the Health Connect APK on older Android), the refusal is diagnosed by reading this app's own ids and versions, never by its text: what is stored at its version or newer is present and the rest is written again, in one read and at most two more writes. `replaceImportedRecord` deletes and rewrites where a provider refuses a newer version. A missing grant, the pause switch and a spent quota (`isHealthConnectRateLimit`, by the platform exception's code) are thrown as they come. Only the watch-only series go to `GarminWellnessRepository`.
- Activity files take their own path, shared with the bulk folder import: `RouteFileImport.toImportWriteRequest` builds the request straight from the parsed file, and `ActivityRepository.writeActivityEntries` writes it. The client ids are a function of a hash of the file's bytes, so a second import of the same file updates its records instead of adding a second workout, and a watch's file is stored as recorded by a watch. A headless import must not go through the entry form's text fields: that lost the seconds, rounded the duration up, and gave every record a random id.
- The OS bond is the security boundary. GFDI's own auth challenge is answered with zeroes, so `OnboardGarminWatchUseCase` treats bonding as mandatory and the companion association as optional.

### `devices/wearos`

A Wear OS watch is a registered device plus a Bluetooth Classic link to the OpenWatch watch app (`:wear`). There is no vendor protocol to speak: the watch runs our own app, and the phone talks to it over an RFCOMM socket on AOSP APIs only.

The phone side is the module `:devices:wearos` (`devices/wearos`, an Android library, namespace `tech.mmarca.openwatch.devices.wearos`), every file below, in the app's package `devices/wearos`. It depends on `:devices:core` and `:wearlink` (`api`: the link's types are in its signatures; the watch app compiles the same module), Hilt, and no other family. It binds itself (`WearOsModule`): its family as `WEAROS`, `WearOsWatchSyncService` into the sync port set, `BluetoothWearOsNodePort` to `WearOsNodePort`, and its startup actor (`phone activity`); its classifier is ranked in the app's `DevicesModule` with Garmin's. It declares no manifest component. It takes the registry, the per-device state (`DeviceStateRepository`, which the app's `DeviceStateStore` implements on `device_state`) and the body profile as contracts, and owns the preferences it reads, `data/repository/contract/WearOsSyncPreferences` (whether to write the breathing rate, on by default, and whether to write the watch's night and naps beside a session another app wrote, also on by default, Health Connect's data source priority then deciding which apps show), which `OpenWatchPreferences` implements (`write_respiratory_rate`, `write_sleep_beside_others`). The link states' sentences (`WearOsAppStatus.messageRes`) are its strings, moved with their translations; "Bluetooth is off", which every family's sync failure says too, is `:devices:core`'s. The classes the sync runs on (`WearOsSessionCache`, the series readers and syncs, the progress) are `internal` to the module; what the watch screen, onboarding, OpenLink and the app's graph use is public: the family, the sync port, the node port and its status types, `WearOsCompanionManager`, `WearOsLinkStore` and its snapshot, `WearOsSyncCursorStore`, the onboarding use case and outcome, the classifier, `isWearOs`. Its tests (155, over `FakeDeviceStateRepository`, mocks of the contracts and health-calculations' wear sleep fixtures) run on the JVM in the phone gate (`:devices:wearos:testCiUnitTest`).

- `WearOsDeviceClassifier` / `WearOsDeviceNames` — claims a scanned device as `(WEAROS, WATCH)` when its name is a known smartwatch family or its SDP record lists the OpenWatch app UUID. A wrist-watch Bluetooth class alone is not enough.
- `OnboardWearOsWatchUseCase` — a single optional `ASSOCIATING` step, no bond and no probe; the device is registered with no capabilities, off the Garmin sync path. The bond itself comes from Android's Bluetooth settings, or from the vendor's onboarding.
- `WearOsNodePort` — the port: pairing and reachability of the watch app. `WearOsAppStatus` is `NOT_PAIRED`, `NO_ANSWER` or `APP_RUNNING`; a bond alone is never shown as connected.
- `BluetoothWearOsNodePort` — the implementation. `WearOsBondMatcher` finds the bonded Classic entry for the registered watch (exact address, then name with a trailing ` LE` stripped: the scan address is a BLE private address), then one `PING`/`PONG` exchange with a ten-second watchdog, once the check has the watch's link. RFCOMM is Classic, so no radio lease is taken.
- `WearOsCompanionManager` — the thin facade the watch screen calls.
- The line protocol itself lives in `:wearlink` (`WearLinkProtocol`), compiled into both apps, at version 5 on both sides: a peer of version 4 (the 0.4.x apps) is answered `VERSION 5 5`, or answers `VERSION 4 4`, and the phone reads either as "update the app" on the side that is behind. The hello offers the phone's highest version; the watch speaks it when it is in its own range, else refuses with that range, and the phone says hello once more, on a new connection, at the highest version both speak (`WearLinkClient.hello`), so a later bump need not cut the link. `WearLinkVersionGoldenTest` holds the hello of every pairing with 0.4.0 and 0.4.1 line for line. `PING`/`PONG`; `SINCE <key> <cursor> <limit>` (`WearLinkSince`) for every series the watch keeps one line per value, asked only for a key its hello announces: `hr` (`HR <epochMillis> <bpm>`), `sm` (`SM` lines, one per clock minute, nineteen integer fields defined in [sleep-minute-features.md](sleep-minute-features.md)), `st` (`ST <minuteStartMillis> <steps>`), `as` (`AS <minuteStartMillis> <decimetres>`, the height climbed; builds that sent whole floors announced `fl` and are not asked), `hv`, `rr`, `o2`, `sk` and `lg` (the entries made on the watch, `WearLinkEntries`). The watch answers from its store by sequence number, the lines as stored, in the order it wrote them, so a row rewritten in place or written late comes again after the rows sent before it, and ends with `END <count> <more> <cursor>`. The cursor is `<store>.<seq>`, the watch's store id and the last row's number, which the phone keeps as it came; a cursor of another store starts from the first row. A time position, `t<epochMillis>`, starts at the first row in sequence order newer than that time: that is how a time cursor of an earlier build hands over (every row newer than it comes, and every row written after the first of those), and how the phone reads a window an estimate needs (filtering to the window). Version 5 replaced the eight per-series requests of version 4 (`HR_SINCE` and the rest). A phone that announces `tm` in its hello gets the watch's clock in `OK`, as `OK <version> <caps,tm> <epochMillis> <name...>`, and logs a skew over two minutes as a direction (`WearOsClock`); a phone that does not, a 0.4.x one included, gets the line it always did. `HR_LIVE <seconds>` (at most 10, below the watch's 15-second idle timeout) is answered with an `HR` line per reading as the sensor takes it, asked only of a watch that announces `hl`, and answered at once with none while the watch is off the wrist; workouts keep `WO_SINCE`, a header with its pauses and route under three keys. `PUT_DAY` (`WearLinkDaily`, asked only of a watch that announces `dy`, added without a version bump) hands the watch the phone's figures for one day and is answered `DAY_OK`. Each reply ends with `END <count> <more>`, and the phone refuses a page whose count differs from the lines that arrived. The watch answers one request after another on a connection, and RFCOMM takes one connection at a time between a phone and a watch on the watch's one channel: while one is open the phone's stack drops a second. So `WearOsSessionCache` is the one owner of each bonded watch's link: every connect, request and close happens in a turn, one at a time, and a call that finds the link busy waits for its turn, up to its own timeout, then runs under a watchdog of that timeout; it never opens a second connection. Turns go first come, first served, except a live heart rate window: it lets every other waiting call go first, and also waits while another caller whose coroutine still runs asked within the last 10 seconds, so a sync's requests follow one another with no window between them. The calls share the watch's one session: one connect and one hello, whose capabilities decide which series are asked for at all. A session is reused while it is under 540 seconds old and its last request went out under 10 seconds ago (the watch closes at 600 and 15), is closed by the phone when the coroutine that opened it ends, when it idles past that, or when a request on it fails, and is replaced once by a new connection when it turns out closed.
- `WearOsWatchSyncService` — the `DeviceSyncPort` for Wear OS. Each series is a `WearSeries` in `WearOsSeries` (its key, how a line reads, a value's time, and for the series written one record per value the record and its grant), pulled with `WearOsNodePort.pullSeries` page by page (`WearOsSeriesReader`). Heart rate first: pulls pages from the watch's cursor (`WearOsSyncCursorStore.seriesCursor`, kept per device and series as `series_cursor_<key>` in `device_state`), writes each page through `ImportedRecordRepository.insertImportedRecords` before asking for the next, and advances the cursor after each write, so a sync that dies mid-way resumes where it stopped. The first pull of a series hands its time cursor (the newest sample time, kept as before) over to the sequence, so no sample already written is sent again: the hour records are keyed on their first sample, so a sample sent twice in another page would be written twice. A sample the watch wrote late, behind the cursor, now comes with the next page. Then steps, the same way: the watch rewrites its newest minute as late steps arrive, and the rewrite comes again by the cursor, so no pull takes the cursor's minute again; the first pull after an earlier build hands over one millisecond before the time cursor, taking that minute once more. Then ascent, the same way, written as floors and filtered by the step minutes around each minute (`WearOsStepContext`): this sync's, and for a minute it did not pull, a window of the watch's steps from the earliest one missing, written to nothing. A minute seen before (not after the ascent time cursor) is written apart from the rest, so an unchanged one does not make the batch fall back to one record at a time. Without the Health Connect grant to write steps, steps and floors stay on the watch and the sync goes on. Then sleep, which keeps its time cursor: the estimate needs the whole night and the phone keeps no minutes, so each sync reads the window again whatever the sequence says. It pulls the minutes from the start of the night the sleep cursor sits in (`WearOsSleepImport.pullStart`), estimates every night those minutes touch and writes one `SleepSessionRecord` per night, skipping a night whose window already holds a session from anywhere else (the vendor's app, the user's own entry), then moves the sleep cursor. Refuses while an activity recording holds the foreground slot. The result counts the heart rate samples, the minutes of steps and the nights (`WearOsSyncProgress`).
- `WearOsEntrySync` — the entries made on the watch (`SINCE lg`, `WearOsSeries.ENTRIES`), pulled after the night series and before the workouts, which stay the last pull since the watch counts a phone's pull by them. Page by page from the watch's cursor (`series_cursor_lg`; the first pull asks from `t0`, everything the watch keeps): each page mapped by `WearOsEntryImport`, split by `partitionByWriteGrant`, and the granted types written with `insertNewer`, so an entry written before is not written again. An entry whose grant is missing is held back: from then on the cursor stays, so it comes again with the next sync, while the other types of every later page are still written, and its grant goes to the result's `skipped` as `RECORDS`, which the watch's card asks for. An entry Health Connect cannot keep at all (a breathing session where it stores no mindfulness, `HealthConnectReads.isMindfulnessAvailable`) or a value it refuses is dropped and the cursor moves past it.
- `WearOsEntryImport` — pure mapping of an entry (`WearLinkEntry`) to its record: water `HydrationRecord`, weight `WeightRecord`, blood pressure `BloodPressureRecord`, a breathing session `MindfulnessSessionRecord` (stamped at its end, its start that many minutes before), a spot heart rate `HeartRateRecord` (one sample), a spot HRV `HeartRateVariabilityRmssdRecord`, body fat `BodyFatRecord`, blood oxygen `OxygenSaturationRecord`, breathing rate `RespiratoryRateRecord`, body temperature `BodyTemperatureRecord` (Celsius), blood glucose `BloodGlucoseRecord` (mmol/L), height `HeightRecord` (whole centimetres on the watch, metres there); keyed `wearos_entry_<type>_<millis>` with the watch's id salt, from a watch, a manual entry for `h` and actively recorded for `m`.
- `WearOsDaySync` — after the zones, the last seven days' figures to the watch (`PUT_DAY`), from any app: per local day the longest night that ended on it with its stages, the latest resting heart rate (`READ_SLEEP`, `READ_RESTING_HEART_RATE`), and the active calories and distance as Health Connect aggregates them (`HealthConnectReads.readDayTotals`, `READ_ACTIVE_CALORIES_BURNED`, `READ_DISTANCE`); `WearOsDaySummaries` is the pure part. A figure whose read is not granted is left out, and a sync that cannot read other apps' data now (`readsOtherAppsDataNow`) sends none, so a background sync never sends figures that leave out every other app. Like the zones it never fails the sync.
- `WearOsZoneSync` — after the workouts, what the watch's zones and figures rest on, as watch settings over `SET_PREF`: the zones' maximum and resting heart rate (`HeartRateZoneBasis` on the declared profile, the year's highest heart rate and the latest night's resting rate) and the body profile a workout's figures need (`body_hg`, `body_cm`, `birth_year`, `sex`; the weight Health Connect's latest, else the profile's). A failed read skips only what it was for, and neither ever fails the sync.
- `WearOsWorkoutFigures` and `WearOsWorkoutMetrics` — a workout's figures, the ones the watch's summary shows (`WorkoutMetrics` in `:wearlink`): `WearOsWorkoutFigures` reads, through `HealthConnectReads`, the watch's own heart rate over the session (`watchBeats`: its hour records under its salt, which the same sync wrote before the workouts, the read widened by an hour both ways since Health Connect finds a record by its bounds), the highest heart rate of the year and the latest night's resting rate for the zones' basis (`HeartRateZoneBasis` on the declared profile, as `WearOsZoneSync` hands it to the watch); `WearOsWorkoutMetrics` (pure) turns them into the session's laps (a kilometre each), a line of its notes (the mean and highest heart rate, the minutes per zone, the TRIMP, and the heart rate recovery's falls where the two minutes after the stop hold a reading a second, `WorkoutMetrics.MIN_RECOVERY_READINGS`, with the reading's verdict where it is not clean: "effort not near-maximal", "approximate") and a `Vo2MaxRecord` at the session's end (keyed `wearos_workout_vo2_<start>` with the watch's salt, written only with `WRITE_VO2_MAX`). `WearOsWorkoutSync` writes them with the session; a workout whose figures cannot be read is written without them. The session's active calories (`WearOsWorkoutEnergy`, once it is written) are `WorkoutMetrics.energy` over the same `watchBeats`, the session's own span, with the resolved body profile (the one `WearOsZoneSync` sends the watch) and the age on the workout's day, the number the watch's summary shows; `WearOsWorkoutImport.activeCalories` only makes it a record (`wearos_workout_energy_<start>`, salted).
- `WearOsHeartRateImport` — pure mapping: one `HeartRateRecord` per clock hour, keyed `wearos_hr_<first sample millis>`, so a re-pull upserts. The watch keeps a week of samples and prunes on its own; nothing is deleted on the phone's behalf.
- `WearOsStepsImport` — pure mapping: one `StepsRecord` per minute, keyed `wearos_steps_<minute millis>`, with the count as `clientRecordVersion`, so a re-pulled minute that grew replaces its record and one that did not is skipped: the write reads this app's stored step minutes first (`insertNewer`), since the platform's Health Connect takes an unchanged minute again without a word and only the read tells what changed. The same minutes become a `StepsCadenceRecord` each (`wearos_cadence_`) and, when a body weight is known (Health Connect's latest, else the body profile's), an `ActiveCaloriesBurnedRecord` each (`wearos_walk_kcal_`, versioned on the step count like the others, so the estimate is frozen at first write and a later weight or session does not revise it) from health-calculations' `insights/WalkingEnergy`: Moore et al. 2021's cadence equation, net of one resting MET. A minute inside any exercise session in Health Connect gets none, so a recorded walk's own active calories are not counted twice. The weight is read once per sync, and only when a minute costs more than rest; without one the walking energy is skipped, as a `NO_BODY_WEIGHT` entry in the result's `skipped`, so the sync card says so. The write grants for steps (Health Connect files cadence under it) and active calories, and the exercise read grant the walking energy filters with, are checked before the pull: a withheld one skips its series, never failing the sync, and the result's `skipped` entry names the series and the grants its button asks for. A minute is estimated when its steps are written (new or grown); one synced without the grant, the weight or visible sessions (in the background without the background-read grant, `HealthConnectGateway.readsOtherAppsDataNow`, or when the session read fails) keeps no estimate. Cadence and walking energy follow the steps insert: a minute Health Connect already held is skipped, except past the step cursor, where only a sync that failed after its steps leaves minutes, so they are tried again. The energy grants and the weight hint are reported only when a pulled minute outside a recorded workout would have had walking energy; without `READ_WEIGHT` the `NO_BODY_WEIGHT` entry carries that grant. The weight and the sessions (`HealthConnectGateway.readExerciseSessions`) are read under `withStrictHealthConnectReads`, so a failed read skips the estimate rather than passing for "none". Cadence and walking-energy writes are optional: a failure is logged and skipped, never failing the sync. Every minute record carries the zone offset in force at its minute. It also stays put when the exercise sessions cannot be seen: in the background without the background-read grant (`HealthConnectGateway.readsOtherAppsDataNow`), where other apps' sessions and weights are invisible, or when the session read fails.
- `WearOsFloorsImport` — pure mapping: one `FloorsClimbedRecord` per minute, keyed `wearos_floors_<minute millis>`, the credited metres over 3 m with the fraction kept, and one `ElevationGainedRecord` of the same credited metres, keyed `wearos_elevation_<minute millis>`; both versioned by the credited decimetres. Height counts only with 10 steps per floor's height in its minute and the one before, so elevator rides and weather drift are dropped; the threshold is an app heuristic. The rule is `AscentCredit` in health-calculations, so the watch app counts floors the same way.
- `WearOsSleepMinuteMapping` — the wire row (`WearLinkProtocol.SleepMinute`, integers) into `domain/model/WearSleepMinute` (physical units, `WearMinuteFlags`).
- `WearOsSleepImport` — pure: the nights a pull touched, each night's rows inside its window, the night through health-calculations' `insights/WearSleepEstimator`, and the record through `estimatedSleepSessionRecord`, keyed `wearos_sleep_est_<night>` with the sync time as version so the later estimate replaces the earlier. The phone stores no minutes: the watch is the store and a whole night window is re-pulled to re-estimate it.
- `WearOsRestingHeartRateImport` — pure: one `RestingHeartRateRecord` per estimated night, keyed `wearos_rhr_est_<night>` with the sync time as version, stamped at the night's end, from health-calculations' `insights/NocturnalRestingHeartRate` (the lowest 30-minute mean of the per-minute heart rate between onset and end, at least 20 minutes with a reading; the rule Dial et al. 2025 report for Garmin). No value while the night is in progress. The sync writes it only when the calendar day of the night's end holds no resting heart rate from elsewhere (the day the app averages), removes its own when one turns up later, replaces a stale version like the session, and fails closed when the read fails, the grants are missing (a `RESTING_HEART_RATE` entry in `skipped`) or other apps' data is unreadable in the background.

The Wear OS night itself is estimated by pure objects in health-calculations' `insights` package, in the order the actigraphy literature settled on: `WearMinuteGrid` (the rows on a one-minute grid, missing minutes absent), `WearStateDetector` (worn or not per minute: charging, off-body, a pulseless run while heart rate is recorded, then van Hees' still-hour rule vetoed by any pulse in the hour; a not-worn minute is a gap to everything after it), `SptWindowDetector` (the night's window: HDCZA on the z-angle change, tightened at its end by the heart rate quantile window), `SleepWakeScorer` (one linear score of Cole-Kripke movement, heart rate volatility after Walch, the z-angle range and the median small z-angle drift, then `WebsterRescoring`), and `SleepStageEstimator.estimateWindow` for the stages, with `Lids` as a prior behind `lidsWeight`. `WearSleepEstimator` strings them together and returns the night with its window and worn counts. The per-minute features are specified in [sleep-minute-features.md](sleep-minute-features.md).

On the watch, `OpenWatchWearApplication` owns `WearGraph`, the app's hand-written object graph (the watch has no DI framework): the store, the link's state (`WearLinkState`), the workout's (`WorkoutState`), the trust store and its Keystore key (`WearSecretKey`), the phone requests' notifications (`WearPhoneRequests`), the debug protocol, the Samsung feed, the recorders and the link server, each built once per process and on first use. `WearAppService` hosts them: at each change of an input it decides what runs with `RecorderPlan` (pure, tested: the settings, the grants, the sensors present, the wrist, bedtime mode, the sleep hold, a workout and its recovery in; one plan out) and hands the plan to every `Recorder` in `WearGraph.recorders`, the heart rate first since the step counter's variant follows it; the recorders and the link tell the running service through `WearGraph.Host`, on the main thread, when the sleep hold, the heart rate's source, the wrist, a workout or a phone setting changes. The service hosts the RFCOMM listener and the recorders, and all write to one `MetricStore`: a single plain-SQLite table keyed by metric and time whose rows are the values' `:wearlink` protocol lines, so the format is defined and tested in one place and the store holds exactly what the phone receives. The store is one instance per process, owned by `OpenWatchWearApplication` and shared by the service, the activity, the dashboard and the tiles, in write-ahead logging so readers never wait on a recorder. Every write goes through one guarded path: one writer at a time, each write one transaction, and a failure (a full disk, a corrupt file) counted for the debug snapshots and answered with false instead of thrown on a recorder's thread; a workout whose header cannot be written keeps its checkpoint, the step recorder keeps its unsaved minutes for the next flush, and the legacy import keeps its file. A link page's "more" comes from the stored rows, not from what decoded, so a row this build cannot read never ends the paging early. Every row also carries a sequence number (store version 3), taken from one counter on every insert and every replace, so a row rewritten in place or written late comes again after the rows already read (`MetricStore.changes`); the counter's high-water mark is kept beside the rows, so pruning never hands a number out twice, and a random store id names the numbering, so a cleared watch starts it over. The migration from version 2 numbers the existing rows in time order (`MetricStoreSequenceTest`). Each series is a `WearMetric` in `WearMetrics`, which names its key (the capability the link announces), its line codec, whether a second value at the same time is kept or replaces the first, and its retention (a week; a month for the workouts and the entries). The entries made on the watch are one such series (`WearMetrics.ENTRIES`, key `lg`, line `LG`, `WearLinkEntries`): what the wearer logs by hand in the quick log (water, weight, blood pressure, a breathing session) and what a spot measurement takes, each flagged `h` or `m`, its values in thousandths of its type's unit. `EntryLog`, built once in `WearGraph`, is their one writer: the store keeps the first value at a time and drops a second silently, so it moves an entry to the first free millisecond under a lock, refuses one its own line would not parse back to, and prunes the month at each write; no screen opens the store to write, and the quick log tile logs its glass of water through it too. Each entry it writes is told to the graph, which asks the quick log tile to show the new water total (`TileService.getUpdater`). A screen follows a metric's writes instead of waiting for its next poll: `MetricStore.updates(metric)` is a count per metric, held by the store instance, that moves after each committed write of that metric (a value stored, a range deleted, rows pruned). The phone's figures for a day (`PUT_DAY`) are no store rows: `PhoneDays` (`WearGraph.phoneDays`, preferences file `wear_day_summaries`, keys `day_<epochDay>`, each the line as it came, the fourteen newest kept) holds them as a `StateFlow`, and `WearReadings` puts them on the sleep, resting heart rate, active calories and distance tiles, today's value as the value now, as for the night's vitals, and the night that ended today gives the sleep detail its stages (`WearUiState.sleepStages`). Rows are pruned by age whether a phone pulled them or not, so `PhonePulls` records when a phone last pulled (the `WO_SINCE` request, the last series of a phone sync; preferences file `wear_phone_pulls`, key `last_pulled_millis`) and `SyncRetention` (pure) warns from the fifth day after it, two days before the pruning reaches unpulled rows: the status screen shows the last pull and the days left, and `SyncReminder` posts a notification once per pull and level (soon, then pruning), checked at the service's start and on an hourly non-waking alarm, and cancelled by the next pull. A workout's route is stored whole (the five-second gap between kept points bounds a day to `WorkoutTracker.MAX_STORED_POINTS`) and thinned to the link's 9000 points when it is read, every second point as often as it takes, so a long workout keeps its end. The link's request handler pages any metric with one generic function. The link's request handler serves every one-line series from the store by sequence number (`MetricStore.changes`, and `seqBeforeNewerThan` for a time position). Adding a metric, one pull request per metric, is: its line in `:wearlink`, a `WearMetric` in `WearMetrics.SERIES` (the link serves it to `SINCE` by its key from then on), a recorder that calls `MetricStore.put`, and on the phone a `WearSeries` and what writes it; the store, its pruning, the link and their tests (`MetricStoreTest`, on Robolectric in the watch gate and on a watch) do not change. `LegacyStoreImport` moves the per-metric databases of earlier builds into the store once, at service start. `HeartRateRecorder` keeps one sample per ten seconds from a `HeartRateSource`, the batched `TYPE_HEART_RATE` listener (`SensorHeartRateSource`) or the Samsung platform (`SamsungHeartRateSource`), and hands each stored sample and each no-contact reading to the minute recorder. While a workout runs the plan asks for the heart rate live (`RecorderPlan.Plan.heartRateLive`, the sensor whatever the source setting): the sensor registers unbatched, empties the other sensors' buffers as often as a batch would come, and the recorder keeps every reading, one a second. A day's heart rate is therefore read with a limit of a 25-hour day at one a second (`TileDay.MAX_HEART_RATE_SAMPLES_PER_DAY`, which `WearReadingsSource` reads every series with), and a mean of samples (the tiles' quarter hours, a day's average) counts them on the ten-second grid (`TileDay.onDayGrid`), so a workout's minutes do not outweigh the rest of the day; the low, the high and the time in zones take every sample. The phone pulls the seconds as it pulls the rest (`SINCE hr`, 2000 a page, one record per clock hour of each page). The recorders reach the Samsung platform only through source interfaces built in `WearGraph`: `HeartRateSource`, `HrvWindowSource` (the night windows) and `SpotSource` (SpO2 and skin temperature; the Samsung source turns the platform's status codes into plain readings), so a recorder never names the platform's client. `StepRecorder` is the non-waking `TYPE_STEP_COUNTER` at the heart rate's report latency, or its waking variant, where the watch has one, while the heart rate is not running and nothing of ours would wake the processor; `StepMinuteCounter` (pure) turns its running total into one row per clock minute, spreading the difference between two readings over the minutes between them, at most the hour before the newer reading (of a longer gap only that hour's share, at the gap's pace), and never writing before the newest minute. A batch is written once, a second after its last event, together with the last reading in one transaction (`MetricStore`'s state table), so a restart neither loses nor double-counts steps. While the watch app is on screen (`MainActivity.onResume` and `onPause` set `WearGraph.setInteractive`, an input of `RecorderPlan`) the plan asks for the steps live (`RecorderPlan.Plan.stepsLive`; not in a workout, which counts its own): the counter registers again without batching, so the dashboard, which reads again on the steps' writes, counts each step within seconds. On a new boot the counter starts again at 0, so its first total is credited from the boot time. `AscentRecorder` reads the barometer (`TYPE_PRESSURE`, no grant) once a second at the same latency; `AscentMinuteCounter` (pure) averages 10 seconds, converts to altitude and counts a rise once it reaches 3 m above the last low point, then with all of its metres, in decimetres, one row per clock minute. The 3 m dead band keeps the barometer's wobble of about a metre from adding up. Each recorder starts only when the watch has its sensor and the grant is in (`ACTIVITY_RECOGNITION` for steps). `SleepMinuteRecorder` keeps one row per clock minute: `MinuteAggregator` (pure) and `AccelerationMinuteFeatures` compute the specification's fields from the batched accelerometer in g, the heart rate samples, the off-body sensor, the charger broadcasts and screen wake-ups. `WornMonitor` is the one owner of the off-body sensor: it hands each reading to the minute recorder and stops `HeartRateRecorder` after 60 seconds off the wrist, starting it again at once when the watch is back on (`WornGate`, pure). Because the off-body sensor may depend on the heart rate sensor on some watches, a screen wake-up or a pulled charger runs the heart rate for another 60 seconds, enough for an "on" to arrive. The accelerometer keeps running: it is cheap, and its events close the minutes. A watch without an off-body sensor keeps its heart rate on. While the heart rate rests, `StepRecorder` switches to the waking step counter; off the wrist it reports nothing, so it wakes nothing. `LiveHeartRate` (one instance in `WearGraph`) serves `HR_LIVE`: each window registers its own unbatched heart rate listener and drops it at the end, only while `HeartRateRecorder` runs, and stores nothing; the window is built on `listen`, a registration that stays until it is closed, which a spot measurement holds too, and so does the heart rate's detail screen while it is shown (`LiveHeartRate.bpm`), whose value is then the heart rate now. On the phone, `WearOsCompanionManager.liveHeartRate` asks for 5-second `HR_LIVE` windows one after another on the watch's one link: 5 seconds, so the session stays inside its 10-second reuse window and a status check, a setting or a sync that comes meanwhile waits at most one window. It pauses after two windows in a row without a reading, or while a sync holds the link, and asks again 15 seconds later. `WearOsWatchPanelViewModel` starts it after the screen's first status check and settings read and shares it `WhileSubscribed`, so it runs only while the watch's device screen is open. The accelerometer needs no permission and shares the heart rate's report latency, so the two batches arrive in one wake-up. That is not enough on the Galaxy Watch8: its accelerometer cannot wake the processor and buffers 48 seconds, and the hub lets a still arm sleep for minutes, so most of a night's movement was lost. While bedtime mode is on (`BedtimeMonitor`: Samsung's `setting_bedtime_mode_running_state`, falling back to Do Not Disturb, which counts only from 21:00 to 09:00 local, `BedtimeWindow`, so a Do Not Disturb or theater mode left on by day is no night), or `SleepHold` (pure, from OpenVitals) sees sleep starting from the closed minutes (ten still, worn minutes with a falling pulse), and the watch is worn and off the charger, the recorder holds sleep (a phone unlock, `PHONE_ACTIVE`, ends an automatic hold). By default the hold is synced wherever the heart rate sensor is a wake-up sensor: no lasting lock, `SensorWakeSync` flushes the accelerometer, barometer and step counter at each heart rate batch. Where the sensor cannot wake the watch, or the wearer or the phone chose it (`WearSettings.syncedSleepHold`; a choice is kept apart from the default, and the phone writing another setting is not one), the hold is a partial wake lock renewed once a minute with a ten-minute timeout (`BedtimeHold`); a synced hold also falls back to the lock while the heart rate is not dense from the sensor. `SleepHoldBudget` counts the minutes held per day, lock and synced apart, for the debug protocol: today's figures in every snapshot, a `SleepHold` `day` line per finished day and an `over_budget` line when the lock passes two hours. The rest of the day it holds nothing. `NightHrvRecorder` measures heart rate variability at night: while bedtime mode holds the processor and the last ten minute rows show a still arm, it listens for five minutes, at most every 30 minutes, to an `HrvWindowSource`: Samsung's raw PPG (`PpgWindowSource`, `com.samsung.sensor.hr_raw` under the heart rate grant, unbatched), whose beats `PpgBeats` finds, or, chosen on the status screen of a watch that has the Samsung Health Platform, the platform's own intervals (`SamsungIbiSource`; see `samsung-health-and-privacy.md`); `HrvRmssd` (pure) turns either into an RMSSD, and the window is stored as one `HV` row only once the minute rows that cover it show the arm stayed still (`NightHrvSchedule`). A watch without the sensor does not announce `hv`. The phone writes each window as a `HeartRateVariabilityRmssdRecord` (`WearOsSeriesSync`, by the watch's cursor, the time cursor handing over on the first pull, as for the breathing rate and SpO2), keyed on its start; without the write grant the windows stay on the watch and the sync card asks for it. `HeartRateRecorder` runs at the plan `WearAppService` gives it (`HeartRateSchedule`, pure, from OpenVitals): the full rate in bedtime mode, otherwise the day setting on the status screen (`WearSettings`): every 10 seconds, batched, or power save, a window about every 10 minutes on `AlarmManager.setAndAllowWhileIdle` (`HeartRateAlarmReceiver`) that closes at the first usable reading. Only the full rate from the sensor counts as dense for the sleep minutes and keeps the step counter non-waking. On a watch with the Samsung Health Platform the heart rate can come from it instead (`SamsungHeartRateFeed`, see `samsung-health-and-privacy.md`). Debuggable builds keep a measurement protocol (`DebugProtocol`, `DebugSnapshots`): a JSON line at each battery percent and each screen, Doze, charger or plan change, with per-sensor delivery counts, plus events from the heart rate, the Samsung feed and the HRV windows. At each service start it writes a `device` line (`SensorReport`): every sensor's type, name, vendor, FIFO sizes (reserved and maximum) and wake-up flag, the batching profile the recorders use (`hub-40s`: one 40-second report latency, tuned on the Galaxy Watch7 and Watch8 hub), and whether the Samsung sources are there (the Health Platform and its version, the raw PPG sensor, the bedtime-mode setting, the diagnostics consent); each recorder's registration is a `registered` line with the variant it took, its sampling period and its report latency (`DebugProtocol.registered`). `scripts/wear-debug-report.py` pulls it and prints the drain per state, the source answers, and per recorder whether a batch fits the sensor's FIFO. A batching profile tested on a watch without the Samsung hub is still to come. `PpgRawLogger` is a research spike for debuggable builds only: a long press on the status screen dumps Samsung's raw PPG sensor to a CSV; nothing depends on it, and the host-side inspection script was dropped in 2026-10. The service's foreground type is `connectedDevice`, plus `health` once the heart rate or step grant is in. Android 16 gates the sensor behind `android.permission.health.READ_HEART_RATE`, not `BODY_SENSORS`; `WearPermissions` picks the right one per release.

### `devices/xiaomi`

The Xiaomi Body Composition Scale S400. The scale takes no connection: it broadcasts each weigh-in as MiBeacon v5 frames in the service data of `0xFE95`, sealed with AES-CCM under a bind key the Xiaomi account issued when the scale was paired. The user pastes that key once; the app never sees the account.

Its platform half is the module `:devices:xiaomi` (`devices/xiaomi`, an Android library, namespace `tech.mmarca.openwatch.devices.xiaomi`), every file of the table below but the codec, in the app's package `devices/xiaomi`. It depends on `:devices:core` and its own codec (`api`), `:wearlink` for `SecretSeal`, WorkManager and Hilt, and on no other family. It binds itself (`XiaomiScaleModule`): its family as `XIAOMI` in the `DeviceFamily` map, `XiaomiScaleListener` as a `CompanionPresenceObserver`, `SystemScaleScanRadio` and `ScaleListeningForeground` to their ports, the one `XiaomiScaleStore`, and its startup actor (`scale listener`). Its manifest declares `ScaleScanReceiver` and `ScaleListeningService`, merged into the app's under the same names; WorkManager's `ScaleListenerWorker` keeps its name. It owns the weigh-in table's contract, `data/repository/contract/ScaleWeighInRepository` (test fixture `FakeScaleWeighInRepository`), which the app's Room implementation keeps implementing (`ScaleWeighInRepositoryImpl`, bound in `di/RepositoryModule`), and takes the registry and the body profile as contracts (`DeviceRegistry`, `BodyProfileRepository`). The notification's two strings are its own, with their translations; the notification icon is `:devices:core`'s. What the Scales screens use stays public: the listener (status, find, set up, rename, release), the store and its config, the writer and `ScaleWriteFailure`, `ScaleWritePermissions`, `ScaleListenerStatus`. Its tests run on the JVM in the phone gate (`:devices:xiaomi:testCiUnitTest`), over the shared fakes.

| Listening | `ScaleScanRadio` (the S400's filters and `PendingIntent` on `devices/core/ble/BleScanner`'s background scan; `devices/core/pairing/CompanionDevicePairing` builds the dialog's filters), `ScaleScanReceiver`, `XiaomiScaleListener` (also the `CompanionPresenceObserver`), `ScaleListeningService` and its `ScaleForeground` port, `ScaleListenerWorker`, `ScaleLog` |
| Pipeline | `ScaleWeighInIngest` (decode, fold into Room, write), `ScaleWeighInWriter` (Room to Health Connect, retries, delete) |
| Family | `XiaomiScaleFamily`: the scale is a registry row of kind `SCALE` and integration `XIAOMI`, kept by `XiaomiScaleListener` beside the store (made at set-up, adopted once at start for a scale set up before, renamed and removed with it). It syncs and streams nothing; its link is up while the scan runs. One scale: setting up another replaces it |
| State | `XiaomiScaleStore` (key, sealed by `SecretSeal`; address, user slot, last failure) |

Notes worth carrying:

- The scan is the system's, started with a `PendingIntent`. It outlives the process, and the system starts `ScaleScanReceiver` for each broadcast that passes the filter. The filter is matched in the Bluetooth chip: `0xFE95` service data, the product id, the "encrypted object" control bits, and the scale's address once known. The scale's idle beacons and a neighbour's scale wake nobody.
- Measured on an S400: the scale advertises idle beacons from the moment someone steps on, and sends the result only once it has finished measuring, as two frames repeated for about a second each, some twenty seconds in. Its timestamp is true UTC. A scale that does not recognise the person shows "----" and broadcasts no result at all. The S400 Pro (MJTZC03YM) sends the same two frames, but marks the second one's missing weight with every weight bit set rather than none; `S400Beacon` reads both as no weight.
- Two seconds on the air is too short for a background scan, which the system runs a tenth of the time, and a twentieth with the screen off on Android 13 and later. So adding a scale goes through Android's companion dialog (`XiaomiScaleListener.findScale`, `CompanionDevicePairing.discover`): it lists the S400s it hears, and the one picked is associated and watched for presence, which is also how the app learns the scale's address and advertised name. `allowSystemWake` asks again for a user who revoked that in Android's settings. When Android reports the scale awake, the listener opens a window of `WEIGH_IN_WINDOW_MILLIS`: it starts `ScaleListeningService`, a foreground service that runs no logic, restarts the scan so it runs at foreground speed from its first moment, and closes both when both frames are in or the window runs out. Verified on a dozing Pixel with the process dead: wake at 0 s, both frames at 23 s. Android tells only the app's primary companion service, `OpenWatchCompanionDeviceService`, which is why that one passes the event to the observers.
- Each frame is still folded into its row as it arrives and the weigh-in is written again if it grows, so a frame missed on a phone that was not woken, or on Android 10 and 11, still saves what was heard.
- Room comes before Health Connect. The scale says each weigh-in once, and a background write cannot ask for a permission. A weigh-in Health Connect has not taken stays pending and is retried on the next frame, at app start, by the worker and when the Scales screen opens.
- A weigh-in is `(scale timestamp, user slot)`. Record ids are built from those two and from no address, since ids travel to other phones. `clientRecordVersion` is the row's `updated_millis`, so a fuller rewrite replaces the earlier records.
- Only what the key authenticates counts. An unsealed object is ignored, and the first sealed frame the key opens says which of the scale's user slots is this person's. A frame from another slot is someone else's body: it is dropped, and only the slot number is kept so the screen can offer to switch. A new key (the scale was paired again in Xiaomi Home) keeps the scale: its address is its identity.
- A reboot, or Bluetooth going off, drops the scan, and no broadcast tells a closed app that Bluetooth is back. `XiaomiScaleListener` arms it again at every process start, and `ScaleListenerWorker` every half hour.
- Android 12 and later listen with the app closed. Android 10 and 11 would need background location for that, which the app does not ask for, so there weigh-ins arrive while the app is open.
- Body composition is an estimate from Sun et al. (2003) in health-calculations' `insights/BioimpedanceComposition`, not what the scale displays. No basal metabolic rate is written: a second source would evict `BmrEstimateService`'s daily estimate on weigh-in days.
- Never log the key, a decrypted payload, a measurement or the address.

### `devices/blestandard`

The devices that speak a Bluetooth SIG standard health profile, as one family, `BLE_STANDARD`: a heart rate strap (the Heart Rate Service, `0x180D`), a blood pressure monitor (`0x1810`), a weight scale (`0x181D`) and a glucose meter (`0x1808`), each by the service it advertises, the measuring ones before a heart rate. It is the first family built on the foundation of Phase 5, and the strap needed nothing outside its module, its Hilt binding and its permission rows: the app's add flow, Home's "Other devices" list, the generic device panel, OpenLink and the measurement sink take it from its contracts. The other three are pushed devices on the same path; they added two record types (their catalog rows and permissions, their spans in `ImportedRecordWrites.timeSpan`) and made OpenLink's `supportsRecording` follow a family's live features rather than the kind.

Trust: the cuff, the scale and the meter are bonded (their profiles require it) and associated, so their readings come over an encrypted link from the device the user paired; the strap is unbonded, as its profile allows, and only read while someone collects it. A reading is parsed whole against its specification's layout or dropped, and logs hold counts and class names only.

Its bytes are the module `:devices:ble-standard:protocol` (`devices/ble-standard/protocol`, plain Kotlin with `explicitApi()`, in the package `devices/blestandard`): `HeartRateMeasurement` (the measurement, `0x2A37`, read whole as the specification lays it out: flags, a uint8 or uint16 value, the sensor contact, the energy expended and the RR intervals in 1/1024 s); `BloodPressureMeasurement` (`0x2A35`: three SFLOAT pressures in mmHg or kPa, the time stamp, pulse, user and status), `WeightMeasurement` (`0x2A9D`: SI or imperial resolution, the unsuccessful value, time stamp, user, BMI and height) and `GlucoseMeasurement` with `GlucoseContext` (`0x2A18` and `0x2A34`: sequence number, base time and offset, the concentration in kg/L or mol/L read as mmol/L, the sample type and location, the meal and carbohydrate), over the IEEE 11073 SFLOAT and the Date Time layout (`HealthValueFields`); `RecordAccessControlPoint` (`0x2A52`: report all stored records, or those from a sequence number on, and the response code); `ReceivedValue`, how a pushed reading is kept, the bytes as sent with the phone's time and offset when they came (`raw1;<millis>;<offset>;<hex>;<context hex>`), so it is read again by the same parser; and `HeartRateSamples` (a clock minute's samples as the family keeps them until Health Connect has them, `hr1;<offset>;<millis>:<bpm>,...`, under the key `hr_<first millis>`, and `HeartRateMinutes`, which cuts a stream into those minutes). Its platform half is the module `:devices:ble-standard` (`devices/ble-standard`, an Android library, namespace `tech.mmarca.openwatch.devices.blestandard`), which depends on `:devices:core` and its protocol and on no other family, and declares no manifest component:

| File | What it holds |
|---|---|
| `StandardProfiles` | The family's persisted names (`BLE_STANDARD`, the record id prefix `ble_standard_`) and the profiles' UUIDs, the Heart Rate and Battery ones taken from the app's `BleUuids` |
| `ProfileRadio` | The port the family opens a link through (`withLink(address, owner) { link -> }`: has, enable a notification or indication, read, write, the values as a flow that fails when the link drops), and `GattProfileRadio`, its implementation over `GattLink` under the radio lease |
| `HeartRateStream` | A strap's stream: one link per strap however many collect it (the device screen, OpenLink), held as `LIVE` while collected and five seconds after, dialled again ten seconds after a drop while collected. Each usable measurement (on the skin, above zero) is a `LiveReading`; each clock minute goes to the `MeasurementSink` as one run, and the minute under way when the stream stops. The battery level is read once per link |
| `StandardMeasurementRecords` | The family's `MeasurementRecords`: a run is one `HeartRateRecord`, auto-recorded by a chest strap; a cuff's reading a `BloodPressureRecord` and its pulse a `HeartRateRecord`; a weigh-in a `WeightRecord` by a scale; a glucose record a `BloodGlucoseRecord` (its specimen source, its relation to a meal and the meal from its context), none for a control solution check. Every id is `ble_standard_<key>` salted by the device. A reading's time is the device's own wall clock read in the phone's offset when it came, or the time it came when the device sent none, one its clock does not know, or one more than ten minutes ahead |
| `PushProfile` | The three pushed profiles by the kind their devices are registered as (`BLOOD_PRESSURE_MONITOR`, `SCALE`, `GLUCOSE_METER`): the service, the measurement, and the key a reading goes under, its user and its own time stamp (`bp_<user>_<yyyyMMddHHmmss>`, `weight_...`), or for a glucose record its sequence number and base time (`glucose_<sequence>_<stamp>`) |
| `MeasurementCollector` | The `CompanionPresenceObserver` the family binds: when an associated cuff, scale or meter comes into range, it dials it under the `SYNC` lease, switches its measurement on (indications) and takes what it sends until it falls quiet for ten seconds, hangs up, or ninety seconds pass; a meter is asked through the control point for its records from the one after the last it gave (`glucose.last_sequence` in `device_state`), all of them the first time, until it answers. Every reading goes to the sink, kept before it is written; what came before a drop is kept too. A device that names a user is one person's: the first id it names is kept (`user_id`), a reading of another is left out, and the unknown user (0xFF) is anyone's |
| `StandardDeviceFamily` | The family and its `DevicePairing`: a device that advertises the Heart Rate Service is offered as a `SENSOR`; pairing asks for no bond and no association (the profile needs neither, and the strap is read only while collected) and registers it with the `HEART_RATE` capability, as the registry has always kept a sensor. Its feature is `LIVE_HEART_RATE`. A cuff, a scale or a meter is bonded and associated (a refused association pairs nothing, and drops the bond the pairing made), registered, and read at once while it is awake; it has no feature. Forgetting one drops its stream, what it kept, and for a pushed device its association and bond |
| `BleStandardModule` | Binds the family and its mapping by `BLE_STANDARD`, the collector as a presence observer, and the radio |

The RR intervals a measurement carries are read and tested, and written nowhere: Health Connect has no beat-to-beat record, and a variability figure from them would be a health calculation, which belongs in health-calculations. Health Connect refuses a systolic pressure over 200 mmHg and a diastolic one over 180, and a glucose level over 50 mmol/L: such a reading gives no record and is dropped. A meter whose memory was cleared starts its sequence numbers again, and is asked from the last one it gave, so its new records come only once it passes that number. Android tells an app a companion device appeared from Android 12 on; before it, a pushed device is read only at pairing. The family's tests run each profile end to end over a fake radio (`FakeProfileRadio`) into the real `DeviceMeasurementSink` and `FakeHealthRecordStore`; nothing of it has run against a strap, a cuff, a scale or a meter.

### `devices/notifications`

In `:devices:core`, with `devices/media` (`PhoneMediaSource` and the media sessions it reads through the listener's component), `devices/weather` (the generic-weather broadcast, its receiver and `WeatherStore`) and `comaps`: the phone's sources a watch relays, vendor-neutral, so a second family relays them without reaching into Garmin. The listener and the weather receiver are declared in that module's manifest under their names, and `Diagnostics` reads its build config's `OPENWATCH_DIAGNOSTICS`, set as the app's is. That the filter's category numbers follow Garmin's enum is the app's `NotificationCategoryParityTest`, the one place both are visible.

`OpenWatchNotificationListenerService` is the platform `NotificationListenerService`. It reads posted notifications, filters them through the pure `NotificationFilter` against the one setting of what to forward (`WatchNotificationPrefsStore`, which the screen, the listener and the bridge all read; the listener's old copy is adopted once and dropped), buffers them in the memory-only `NotificationStore`, and hands them to `GarminNotificationBridge`. It touches no Bluetooth; the bridge owns the forwarding. Nothing is written to a file or a database.

### Hilt wiring

A device family that is a Gradle module of its own binds itself (the owner's decision 4, 2026-11, which reversed the rule that only `di/DevicesModule.kt` bound the layer): its Hilt module, `@InstallIn(SingletonComponent::class)` and in the family's package, binds its family into the `DeviceFamily` map under its persisted name (`@StringKey`, which `DeviceFamilies` checks against the family's id), its sync port and presence observer `@IntoSet`, its ports and stores, and its startup actors. Hilt and KSP run in the module, so the app's graph installs the module from its classes; the app names the module in its build file and nowhere else. `:devices:garmin`'s is `GarminModule`, `:devices:wearos`'s `WearOsModule`, `:devices:xiaomi`'s `XiaomiScaleModule`, `:devices:ble-standard`'s `BleStandardModule`.

`di/DevicesModule.kt` binds what every family shares and the families still in the app: `BleWatchPairing` to `WatchPairingPort`, `DeviceMeasurementSink` to `MeasurementSink` with the families' `MeasurementRecords` map (`@Multibinds`, so none is needed) and its startup actor, `RegisteredFamilies` (the families' persisted names, from the map's keys through providers, which the registry reads its rows against), `AndroidSyncWakeLock`, the composite `DeviceSyncPort` over the set, the classifiers in their order, the schedule's startup actor, and the auto-sync interval store (every watch's interval is kept in the Garmin store, under its old key). The app's `RepositoryModule` binds the contracts the device modules take to the app's implementations: `DeviceRegistry`, `DeviceStateRepository`, `BodyProfileRepository`, `ActivityRepository`, `GarminWellnessRepository`, `GarminSleepMinuteRepository`, `GarminActivityPreferences`, `ScaleWeighInRepository`, `WearOsSyncPreferences`. Everything else is constructor injection. Only `:app` and the device modules declare Hilt modules: not the app's `devices/` packages, not `:devices:core`, a contract or a protocol module. A device module depends on no other device module, no feature and not on the app. `DevicesLayeringTest` holds the three (and that each device module binds its family), and `HiltGraphTest` that every family, sync port, presence observer and classifier is in the built graph.

The BLE discovery scan the add-a-device flows use lives in `sensors/ble` (`:devices:core`), trimmed to discovery: a family that streams a sensor live (a heart rate strap) opens its own link through `GattLink` and hands its readings out as `DeviceFamily.liveReadings`, which the device screen and OpenLink collect.

### Two ways in: pairing and pushed measurements

A family whose devices need no flow of their own (no bind key, no watch app) declares a `DevicePairing` on its `DeviceFamily`: the services its devices advertise, which scanned device it claims and as what kind, and how one is paired (a bond, a companion association, then its registry row). The app then lists its devices in Home's "Other devices" section and pairs them through one generic dialog, and opens them on the device screen with the generic panel (`features/watches/generic/GenericDevicePanel`): the live heart rate while the screen is open, when the family streams one, and what the device pushed that waits for Health Connect, with the grant that would let it. The section shows nothing while no family declares a pairing.

Data reaches Health Connect two ways. A watch is pulled: `DeviceSyncPort`. A device that pushes (a cuff that indicates a reading, a meter or scale that hands over what it stored, a strap that streams) gives each measurement to the `MeasurementSink`: `DeviceMeasurementSink` (`:devices:core`, `devices/core/measure`) keeps it in the device's own `device_state` first (key `measurement.<its key>`, value the family's payload; it goes with the device), then reads every kept one back through the family's `MeasurementRecords` (bound `@IntoMap @StringKey` by family id; the app declares the map with `@Multibinds`), writes in one batch through the record sink what the grants allow, forgets what was written and stamps the device's last sync. One whose first record's grant is missing stays kept, the grant named in `backlog`; one that gives no record is dropped; a failed write keeps them all. The next measurement, the device screen (on a grant) and every start (`pending measurements`) try again. The family builds each record's `clientRecordId` from the measurement's key, salted by the device (`saltedRecordId`), so a measurement handed over twice is one record. It is the S400 pipeline's rule, Room before Health Connect, for any family; the S400 keeps its own table.

## Modules `:core:model` and `:core:fit`

The app-local code that nothing in the rest of the phone app sits below, in two pure-Kotlin modules (`openwatch.jvm.library`, JDK only, no Android):

- `core/model` (`:core:model`): the packages `domain/model` (the device, sleep-minute, scale and activity models), `domain/preferences` (the unit and theme choices, and the `SystemUnitSystemProvider` interface) and `core/geo` (coordinate parsing); the plain values the device protocols take from the platform sources, `devices/weather/WeatherSnapshot` and `devices/notifications/NotificationMessages`, and the scan filter `devices/core/ServiceDataFilter`; and in `core/performance` `RunSuspendCatching`, the injected `DispatcherProvider` and the `@ApplicationScope` qualifier, which the device modules inject as the app does (it takes coroutines as `api` and javax.inject for the qualifier). The calculations it once held (the sleep and walking estimators, body composition, workout energy) are [health-calculations](#health-calculations-composite-build-health-calculations)', which it takes as an `api` dependency, since the activity models carry its route and lap types.
- `core/fit` (`:core:fit`): the FIT container codec, package `core/fit`: the decoder, the encoder, the CRC, the 16-bit float. What a record means stays with the code that reads it.

Package names are unchanged, so an import does not say which module a class is in. `:app` depends on both. The one piece of `domain/preferences` that reads the platform, the locale's measurement system, is the app's `core/presentation/LocaleUnitSystemProvider`, bound to the interface in `di/AppModule`. Nothing in either module is injected: they hold no Hilt module, and their classes are constructed by the app's repositories and the app's `di/` modules.

The wear sleep fixtures the app's Wear OS sync tests use are health-calculations' test fixtures (`testFixtures("tech.mmarca.healthcalculations:health-calculations")`); these modules have none of their own.

The modules exist for the build and for the boundary: a change elsewhere leaves their compile and test results in the build cache, and the compiler, not a test, keeps Android and the rest of the app out of them. Their tests are plain JUnit (`:core:model:test`, `:core:fit:test`, in `verifyCiUnitTest`, as are `:core:devices-api:test`, `:devices:garmin:protocol:test` and `:devices:xiaomi:protocol:test`; `:core:health-api`, an Android library, runs `testCiUnitTest` and `lintCi`), and Android lint still checks them, the contracts and the protocol modules (`com.android.lint` with the app's rules, each module's `lint` in `verifyCiLint`), without its API-level check (see [development.md](development.md#lint)). What does not belong here: anything with an inbound dependency from `data/`, `healthconnect/` or `features/`, resources, and Hilt wiring. The architecture ratchets walk them through `LibraryModuleRoots` in the app's architecture tests, and `LibraryModuleRootsTest` fails on a module under `core/` or `devices/` that is not listed there.

## Shared module `:wearlink`

The phone-to-watch link, in `wearlink/`, pure Kotlin on the JDK with no Android dependency, compiled into both `:app` and `:wear`. It exists because both apps need exactly the same protocol and the copied file it replaced was held in sync only by a test. Package `tech.mmarca.openwatch.wearlink`:

- `WearLinkProtocol` — the line grammar over the RFCOMM socket: words, limits, the `SM` row type and every format and parse function. The `SM` fields are specified in [sleep-minute-features.md](sleep-minute-features.md).
- `WearLinkPreferences` — the watch settings the phone reads with `GET_PREF` and changes with `SET_PREF`: their keys and values, opaque tokens on the wire, and the read-only keys that say what the watch can offer.
- `WorkoutMetrics` — what a workout comes to, the watch's summary and what the phone writes being one number: the time-weighted mean and the highest heart rate, the time in zones, the TRIMP, the energy, the kilometre splits, the VO2max and the heart rate recovery after the stop with its verdict (`HeartRateRecoveryQuality`: clean, approximate, not comparable, invalid, no data), each health-calculations' (`timeWeightedMeanHeartRate`, `HeartRateZones.timeInZones`, `workoutTrimp`, `estimateWorkoutEnergy`, `buildActivitySplits`, `estimateRouteVo2Max`, `calculateHeartRateRecovery`) over the workout's active time, its session less its pauses; only the pace, the distance over that time, is worked out here. The mean, the zones, the TRIMP and the energy's mean heart rate all count each pair of readings for the time between them, a gap of more than five minutes for nothing (health-calculations' one gap), so readings at uneven intervals do not skew them.
- `WearLinkDaily` — the `PUT_DAY` line (`DaySummary`): a day number, the night's minutes asleep, awake, REM, light and deep, the resting heart rate, the active kilocalories and the metres, each a whole number within what a day holds or `-`, and the capability `dy`.
- `WearLinkEntries` — the `LG` line of an entry made on the watch (`WearLinkEntry`): its time, a type token (`water`, `weight`, `bp`, `mindful`, `hr`, `hrv`, `bodyfat`, `spo2`, `breath`, `temp`, `glucose`, `height`; a later one is skipped by a build that does not know it), the value and the second value in whole thousandths of the type's unit (the diastolic of `bp`), and `m` for a value a sensor measured or `h` for one entered by hand. The watch serves it to `SINCE lg`.
- `WearLinkLines` — the framing, defined once for both ends: UTF-8 lines, `\n` terminated, a trailing `\r` tolerated, a line over 512 bytes closes the connection. The reader takes the socket's bytes a chunk at a time (up to 4 KB, whatever has arrived) and keeps what follows a line for the next, so a connection has one reader.
- `WearLinkToken` — the secret a phone presents on every connection: 32 random bytes as Base64, compared in constant time. The bond says the devices know each other; the token says this app on this phone is the one the wearer allowed. The phone keeps one per added watch (`WearOsLinkStore`, keyed by the address the watch was added under, since pairing again can list the bond under another address) and drops it when the watch is removed; the watch keeps one per phone address. A known phone presenting another token, as after a reinstall, is asked about again like a new one, and allowing it replaces the old token.
- `SecretSeal` — how both apps keep a secret at rest: AES-GCM under a key made in and held by the Android Keystore (`core/security/KeystoreSecretKey` on the phone, `WearSecretKey` on the watch), stored as `v1:` and Base64. It seals the link tokens on both sides and the scale's bind key. A value from before sealing reads as it is and is sealed on that read; a value whose Keystore key is gone opens to nothing, so the watch asks the wearer again and the scale screen asks for the key.

Its one dependency is health-calculations (`api`: `WorkoutMetrics` takes its body profile and returns its results), a composite build of plain Kotlin like this module, so neither app gains a library by it. Its tests run in both gates (`verifyCiUnitTest` and `verifyWearCi` depend on `:wearlink:test`), its lockfile is `wearlink/gradle.lockfile`, and the file-size ratchet holds its files to the same limit as the phone app's.

## Module `:devices:core`

The device layer's shared platform half, in `devices/core/`: an Android library (`openwatch.android.library`, namespace `tech.mmarca.openwatch.devices.core`) in the app's package `devices/core`, so an import does not say which module a class is in. Beside it are the phone's sources a watch relays, in their own packages: `devices/notifications` (with `data/repository/WatchNotificationPrefsStore`), `devices/media`, `devices/weather` and `comaps` ([`devices/notifications`](#devicesnotifications)); the FIT activity file import, `activityimport`, with the strings of its exercise types; and `core/performance/AppForegroundGate`, which the Garmin bridge and the app's gateway read. It holds what every family uses and no family owns: the radio lease, `DeviceLog`, `ble/BlePermissions`, `ble/GattLink` and `ble/BleScanner`, the pairing implementations with `OpenWatchCompanionDeviceService` (declared in the module's manifest, merged into the app's), and the sync machinery (`DeviceSyncController`, `WatchAutoSyncScheduler` and `WatchAutoSyncWorker`, `SyncBudget`, `AndroidSyncWakeLock`, `EstimatedSleepRecord`). The worker keeps its class name and package (WorkManager stores the name), and its work keeps its names.

It depends on `:core:devices-api` and `:core:health-api` (`api`: their types are in its signatures), on WorkManager, AndroidX Activity (the companion dialog's result launcher) and Hilt, with KSP: the companion service is an `@AndroidEntryPoint` and the worker's entry point an `@EntryPoint`, which Hilt aggregates into the app's graph from the module's classes. It declares no Hilt module; the app's `di/DevicesModule.kt` binds its pieces. `DeviceLog.isEnabled` is its build config's `DEVICE_DEBUG_LOGS`, set to match the app's `BuildConfig.DEBUG` (a library's own `DEBUG` is true in the debug APK the release pipeline publishes, which is not debuggable). Its tests (`:devices:core:testCiUnitTest`, in `verifyCiUnitTest`: the lease, the controller over `FakeDeviceRegistry`, the link's redial, the grants) and its lint (`lintCi`, in `verifyCiLint`) run in the phone gate; its lockfile is `devices/core/gradle.lockfile`. Its lint sees the module's manifest, not the permissions the app declares, so the calls that need a grant carry `@SuppressLint("MissingPermission")` and check it at run time, as before. It also holds the notification icon the device services and the OpenLink streaming notice share (`ic_stat_activity_recording`), and its test fixtures are what the device modules' tests and the app's share: `devices/FakeSharedPreferences` and `core/security/testSeal()` (a `SecretSeal` on a software key).

## Module `:wear:recording-core`

The watch app's code that needs no Android, in `wear/recording-core/`: plain Kotlin on the JDK, like `:wearlink`, compiled into `:wear` only. Package names are the watch app's (`tech.mmarca.openwatch.wear` and `.wear.workout`), so an import does not say which module a class is in. It holds what the recorders decide and compute, and nothing that reads a sensor, a preference or the store:

- `RecorderPlan` and the `Recorder` interface the recorders implement, `HeartRateSchedule`, `WornGate`, `BedtimeHold`, `BedtimeWindow`, `SleepHold` and `SleepHoldBudget`.
- `MinuteAggregator` (the sleep-minute rows), `StepMinuteCounter`, `AscentMinuteCounter` and `NightHrvSchedule`.
- `WearMetric` and `WearMetrics`, the series the store keeps: keys, line codecs, retention. The store itself (`MetricStore`, SQLite) stays in `:wear`, and so does `EntryLog`, the entries' writer.
- `EntryDays`, the entries made on the watch by local day: the water by the hour, the weights, the newest value of a type.
- `Stillness`, whether the arm stayed still through a spot HRV, from the accelerometer, and `SensorClaim`, one user of a sensor at a time (the night's HRV window or a spot HRV).
- `WatchSensors`, what the watch has to measure with, and `SpotKind`, the spot measurements as plain kinds, with `SpotEvent`, `SpotFailure` and `SpotRules`, when a measurement has its reading and what it is.
- `SyncRetention`, when the wearer is warned that unpulled rows are about to go. `PhonePulls` (the preferences) and `SyncReminder` (the notification) stay in `:wear`.
- `WatchPreferences`, `WatchAbilities` and `WearPreferenceCodec`, the settings as one value and as the `GET_PREF`/`SET_PREF` tokens (the zones' heart rates and the body profile a workout's figures need, `body_hg`, `body_cm`, `birth_year` and `sex`, which the phone sets, among them; `WatchPreferences.bodyProfile()` reads the latter as health-calculations' `BodyProfile`), `MeasurementSource`, the raw sensors or the Samsung platform, and `UnitSystem`, with its water conversion. `WearSettings` keeps them in its preferences file, in `:wear`, and names the source `WearSettings.Source`, a type alias, so the entry names it stores do not change.
- `TileDay` and `TileHeartRate`, the tiles' day axis and headline.
- `Choices`, an ordered choice the wearer edits (the dashboard's tiles, the quick log's entries): stored as names, switched, moved past the items not shown. `WearTilePreferences` keeps the tiles' choice in `:wear`, `WearQuickLogPreferences` the quick log's. `QuickLogItem`, the entries the quick log can offer, each by the entry type it logs.
- `workout/`: `WorkoutTracker`, `WorkoutCheckpoint`, and `WorkoutStore` over the `WorkoutRows` interface, which `:wear` implements on the store (`MetricStoreWorkoutRows`); `AutoPause` (a stop and a start from the GPS speed), `RestDetector` (a rest from the accelerometer), `RecoveryPlan` (what a stop does about the heart rate recovery, `RecoveryAtStop`, on health-calculations' zones) and `ActivityDetector` (a walk or a run in the step minutes). `ActivityDetectionMonitor`, which offers what the detector sees, stays in `:wear`.

What stays in `:wear` though it is plain Kotlin: the UI state (`WearUiState`, `WorkoutState`, `WearLinkState`, the status screen's), which the screens and the coroutines around them own, and the Samsung client's point parsers in `samsung/`, whose recorded-callback fixtures the device test shares. Its dependencies are `api` on `:wearlink` (its rows are in the public signatures) and `implementation` on health-calculations; its lockfile is `wear/recording-core/gradle.lockfile`. The watch gate runs its tests, on the JVM with no Robolectric, and Android lint over it (`com.android.lint`, with the Android modules' rules from `build-logic/` and its own `lint-baseline.xml`), since lint checked these files in `:wear`.

The source ratchets in `:app`'s architecture tests (file size, function length, the log callers and the log interpolation, `runBlocking`, `runCatching` around an `await`) read the watch app and this module as they read the phone app, and the watch gate runs them (`:app:architectureTest`). `WearPackageDirectionTest` holds the watch app's package direction, as `PackageDirectionTest` holds the phone's: the screens (`features`, `ui`) sit on top and only the activity and the navigation host import them, and the Samsung client is named only by `WearGraph`, which builds its sources, with an allow-list of today's exceptions.

## health-calculations (composite build `health-calculations/`)

The health calculations OpenWatch and OpenVitals share live in their own repository, [Hale-MTU/health-calculations](https://github.com/Hale-MTU/health-calculations), a git submodule at `health-calculations/` taken as a composite build (`includeBuild("health-calculations")`, dependency `tech.mmarca.healthcalculations:health-calculations`). It is plain Kotlin on the JDK with no dependency, so the phone app and the watch app take the same code: `:core:model` and `:wearlink` with `api` (so `:app` sees it, and both apps' workout figures are `WorkoutMetrics`'), `:wear` and `:wear:recording-core` with `implementation`.

The submodule's pointer must name a commit on the library's default branch: merge the library's pull request first, then move the pointer, here and in OpenVitals. A pointer at a commit that only a pull request branch holds builds until that branch is deleted, and then no fresh clone can check the submodule out. `scripts/ci-submodule-pointers.sh` checks every submodule and is a job of the gate (`submodule-pointers` in `verify.yml`), so a pull request that points at an unmerged library branch stays red until the library is merged.

The phone app reads its `insights` (the Wear OS night, the nocturnal resting heart rate, body composition, workout and walking energy, the activity type a file names), its `model` (the exercise session, the sleep-minute rows) and its `preferences` (the body profile). The watch reads its `signal` package (beats from the PPG, RMSSD, respiratory rate, the accelerometer's minute features, the Samsung inter-beat intervals) and `insights/AscentCredit`, which the phone's floors import reads too, so both count the same climb. The recorders, holds and gates that decide when a sensor runs stay in the watch app (`:wear`, the pure ones in `:wear:recording-core`): they control the device, they compute no figure.

Health Connect's exercise and segment types are copied in the library under their Health Connect names; `ExerciseTypeMirrorTest` in `:app`, the module with Health Connect on its test classpath, checks every value against the real classes, both ways. A calculation is changed in the library and reaches the apps when the submodule moves; it moves in OpenVitals in the same step, so both apps give the same number.

## OpenLink host (`link/`, composite build `openlink/`)

OpenVitals, and any app the user allows, reaches OpenWatch through OpenLink, a bound
service with an AIDL interface. The library is a git submodule at `openlink/` taken as a
composite build (`includeBuild("openlink")`, dependency `tech.mmarca.openlink:host`); its
protocol and trust rules are `openlink/docs/spec.md`. Health data still travels through
Health Connect; OpenLink carries the body profile, the device list with "sync now",
recording sessions and live readings.

The host is the module `:link-host` (`link-host/`, package `link`), an Android library: the
service, declared in the module's manifest, the capabilities, the first-party list
(`res/values/openlink.xml`) and the streaming notification with its strings. It depends on
`:core:data` (the registry, the body profile), `:devices:core` (the families, the sync
controller) and `:core:ui` (the notification's list of names), never on a device family or a
screen. The trust store and the binder are built in the app's `di/LinkModule`, which also makes
the one way in that names the app's activity: `ConnectedAppsIntent`, the Connected apps screen a
consent request and the notification open.

- `OpenWatchLinkService` is exported with no permission (a custom one is granted only if
  OpenWatch was installed first, and a normal one protects nothing); the trust is decided
  per call by `OpenLinkHostCore` from the caller's signing certificate. `res/values/openlink.xml` lists the certificates trusted without asking
  (OpenVitals' release upload key and its Play app-signing key); any other app waits on the Connected apps screen.
- `OpenWatchLinkCapabilities` answers from memory on the binder thread: `LinkDevices` (a
  StateFlow over the registry, each device's family for what it can do and whether its link is
  up, and the sync controller; every device goes by its registry id, the scale's included, so
  no address leaves the phone; kind and integration are OpenLink's open sets, so a new family
  goes by its own persisted name, and a client on an older library leaves it out),
  `LinkProfileSync` (last writer wins, stamped in `openlink_profile`), and
  `LinkLiveSessions`.
- A recording session cannot start a workout on either watch; it keeps the watch's live
  readings flowing, from the device's family (`DeviceFamily.liveReadings`: a Garmin held link
  with its heart-rate and steps streams on, through `GarminNotificationBridge.holdLiveForSession`,
  without touching the user's switch; the Wear OS app's live heart rate) and reports `RECORDING` on the first reading. A live
  subscription batches those readings once a second to the app that owns the session.
- A pending app gets no card on the home screen: any app can say hello, and `MainActivity`
  is exported, so a card could be raised from outside. Pending apps head the Connected apps
  list, and a client opens that screen from a tap through its `consentIntent`.
- Only a first-party package name (`openlink_first_party_packages`) under one of
  `openlink_known_signers` is trusted without asking (`FirstPartyApps`); the same key under
  another name asks like any app. A first-party name that came under another key gets a
  warning on its card, and so does an app whose label carries a first-party name
  (`openlink_first_party_names`, ignoring case, spaces and punctuation) under another package.
  Every card but a first-party client's shows the package and the signer's first 64 bits
  (`signerFingerprint`), since a label is the app's own choice. What the user switches off
  stays off through the app's next hello.
- While the Connected apps screen shows, `MainActivity` drops touches that came through
  another app's window (Compose ignores a view's `filterTouchesWhenObscured`), and from
  API 31 other apps' overlays are hidden.
- Connected apps shows per app "In use now" (`OpenLinkHost.connected`) or the last
  connection, each session's state (`OpenLinkHost.activeSessions` joined with
  `LinkLiveSessions.activity` in `linkSessionStatuses`), and the last profile received.
  `LinkStreamingNotifier` keeps a silent notification up while any session holds a watch
  ("Streaming heart rate to OpenVitals").
- `OpenWatchLinkPublisher`, started with the app, sends device and local profile changes to
  bound clients.

Proposed, not built: security fixes and workouts the watch records itself, in
[openlink-recording-proposal.md](openlink-recording-proposal.md).

## Cross-Cutting Rules

These rules hold app-wide. Breaking one is not a local decision.

### 1. One foreground service, and only for the scale

The bathroom scale is the one service the app starts without a tap. When Android reports the
associated scale awake, `XiaomiScaleListener` starts `ScaleListeningService` (`connectedDevice`,
silent notification) for at most 45 seconds, because a background app's scan is too slow to
catch a result that is on the air for two seconds. Someone stepping on a scale is the user's
action; nothing else in the app may copy this. `ScaleListeningForeground.raise` starts nothing
when the app is already at foreground importance.

A Garmin watch sync runs with **no** foreground service of its own; its process-priority story
is the companion-device association. `WatchAutoSyncWorker` is a plain `CoroutineWorker`, never
an expedited or foreground one, as is the scale's half-hourly `ScaleListenerWorker`.

### 2. One BLE radio, leased per address

Every subsystem that opens a BLE link to a device goes through `RadioLeaseRegistry`. The six
owners are `SYNC`, `FIND`, `SETTINGS`, `NOTIFICATIONS`, `PROBE` (the add-a-device flow reading
a device's GATT services) and `LIVE` (a live stream, held while someone collects it), and on a
given address they mutually exclude: a file sync, a
find-my-watch ring, an open settings link, the notification forwarder and a probe cannot hold
the same watch at once. `GattConnectionRatchetTest` keeps `connectGatt(` to `GattLink`, whose
owners hold the lease for the link's life, and to the add-a-device probe, which holds `PROBE`.

- Leases expire, so a crashed holder cannot wedge the radio. A fresh lease lasts 30 s, a
  renewed one 15 s.
- `request()` registers a waiter; the current holder's next renew then fails, which is its cue
  to drop the link. That is how the indefinitely-held notification forwarder and settings link
  yield to a sync. A waiter expires after 10 s.
- Work with an end (`withRadioLease`: a sync, a find, an upload) renews with
  `yieldToWaiter = false` and keeps the radio until it is done.
- `release()` leaves a short settle window rather than clearing the entry.

A lease guards a link. The scale listener opens none: it only scans. The Wear OS link is RFCOMM
on the Classic radio and takes no lease either.

### 3. Health Connect is reached through `HealthConnectGateway` only

[`HealthConnectGateway`](../../core/health/src/main/kotlin/tech/mmarca/openwatch/healthconnect/HealthConnectGateway.kt)
is the one class that holds the client. It is the module `:core:health` (`core/health`), with
the record sink's implementation (`ImportedRecordRepository`), the activity write path
(`ActivityRecordWriter`, `ActivityWriteRepository`), the sync switch's gate, the intents into
Health Connect's own screens and `HealthDataCatalog` with its strings; it depends on
`:devices:core` for one class, the foreground gate that drops the cached grants. A device never
takes it: it takes the contracts of
`:core:health-api` (`core/health-api`, an Android library since Health Connect's records are
the signatures), bound in `di/RepositoryModule`. It reads through `HealthConnectReads`, which
the gateway implements, and writes through the record sink `HealthRecordStore`, which
`ImportedRecordRepository` implements, with the helpers of `ImportedRecordWrites.kt` (outcomes
per record, batches of at most `MaxRecordsPerInsert`). The paused-sync exception and
`isHealthConnectRateLimit` are the module's too; `FakeHealthRecordStore`, its test fixture, is
Health Connect's writes in memory as measured. The devices write through
`ImportedRecordRepository.insertImportedRecords` with a deterministic `clientRecordId`, so a
re-sync upserts; Health Connect replaces a record only when its `clientRecordVersion` is
higher, so a record that is rewritten as it grows carries a rising version. Activities go
through `ActivityWriteRepository` and `ActivityRecordWriter`, the write path copied from
OpenVitals so the records are the same ones.

**A reader is strict.** Every read in the gateway throws when it fails. Nothing here turns a
refusal into an empty list, because every caller saves what it read: a null weight would skip
an estimate, an empty session list would double-count a workout.

**A writer checks that it can see other apps' data.** In the background, without the
background-read grant, Health Connect answers a read with this app's own records only, and
raises nothing. `HealthConnectGateway.readsOtherAppsDataNow()` is the test: a started
Activity, or the grant. Code that saves what it read while no screen is up calls it first and
skips the pass when it is false.

There is no rate-limit backoff, no call pacer and no call tally: the devices issue a handful
of reads per sync, and there is no dashboard fanning out dozens. If a quota refusal is ever
seen, OpenVitals' `HealthConnectRateLimit.kt` is the shape to copy.

### 4. A missing permission is a type, not a message

`Throwable.isPermissionFailure()` (`core/presentation/PermissionFailure.kt` in `:core:model`, so the device modules share it) is the single predicate
for "this failed because a permission is missing". It walks the cause chain looking for
`SecurityException`, because Health Connect throws that for an ungranted read or write and the
repositories throw the same type when they short-circuit a call whose permission they know is
missing. `ScreenErrorHandler.handle` checks that predicate first and returns
`ScreenError.PermissionDenied`, which the screens render as a grant affordance. Reuse it; do
not pattern-match on exception messages.

Any other failure becomes the screen's translated fallback (`ScreenError.Text`), never the
exception's own text, which is English and meant for the log. A state holder that catches a
failure puts it in its state as `error: ScreenError?` and the screen shows it with
`ScreenErrorContent`; it never turns a failed read into "nothing there".
`SwallowedFailureRatchetTest` fails on a `ViewModel` that catches an exception without a name.

### 5. Nothing waits on the main thread

- Health Connect and Room calls are `suspend` and run on `dispatchers.io`. Inject
  `DispatcherProvider` so tests can swap it.
- No `runBlocking` in `src/main`. `NoRunBlockingRatchetTest` holds the (empty) allow-list.
- A receiver never holds a broadcast for a Health Connect read. A scale broadcast is stored
  first: `ScaleWeighInIngest` folds the frame into Room, then writes to Health Connect on its
  own scope.

### 6. Text that leaves the app is structure, not data

A log line never splices in a value: log a count, a class name, or pass the throwable as the
last argument. `LogMessageInterpolationRatchetTest` holds the count of log calls that splice in
an exception message, and it may only fall. On the watch, a line that has to carry a value for
diagnosis (a reading, a time, a sensor's name) goes through `DebugProtocol.log`, which writes only
in a debuggable build and never builds the text otherwise; R8 also strips `Log.i` and `Log.d` from
a release (`wear/proguard-rules.pro`), but a build that skipped R8 would keep them. Nothing in OpenWatch builds a report or a crash
draft; if one is added, it must seed sentinel values in a test and assert none comes out, as
OpenVitals' reports do.
